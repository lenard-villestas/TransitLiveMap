Calgary Transit Live Tracker

A live web map of Calgary Transit buses and CTrains, built with a Python/FastAPI backend and a React + MapLibre GL frontend.

Overview

The app polls Calgary's public GTFS-realtime feeds, resolves each vehicle's trip to its route and shape, and serves clean JSON to a vector map. Vehicles snap to and glide along their route polylines (rotating to their travel bearing); stops and predicted ETAs appear as you zoom in; and you can track any vehicle to its next stop with a follow-cam and a live ETA / Late countdown.

Architecture

Clients never hit Calgary's feed directly. A Python backend decodes the GTFS-realtime protobuf, joins each trip_id to its route via the static GTFS schedule, caches the result in memory, and hands cheap JSON to every client. A background thread does the polling so the blocking network calls never freeze the web server. 

Calgary Open Data (GTFS-RT protobuf, ~30s cadence)
        |  poll every 15s, dedupe on header timestamp
   Python / FastAPI backend
   |-- load static GTFS once at startup (routes, trips, shapes, stops)
   |-- background thread polls vehicle positions + trip updates
   |-- in-memory caches (latest snapshot + stop/trip arrival indexes)
   |-- GET /api/* -> clean JSON
        |  fetch /api/vehicles every 15s
   React + MapLibre frontend
   |-- GPU symbol layers for vehicles + stops (GeoJSON sources)
   |-- requestAnimationFrame loop: glide along route shapes + follow-cam
   |-- stop/vehicle click -> ETA popup; track a bus to its next stop

Run locally

Backend

python -m venv .venv
source .venv/bin/activate            # Windows: .venv\Scripts\Activate.ps1
pip install -r requirements.txt
python -m uvicorn server:app --reload --app-dir backend   # http://localhost:8000

Frontend (React)

# dev (hot reload), in a second terminal — proxies /api -> :8000
cd frontend-react
npm install
npm run dev                          # http://localhost:5173

# production build — uvicorn then serves the bundle at :8000
npm run build

On first start the backend downloads Calgary's static GTFS (a few seconds), then polls the live feeds every 15 s. An optional VITE_MAPTILER_KEY in frontend-react/.env selects the MapTiler basemap; left blank, the app uses the keyless OpenFreeMap basemap. See frontend-react/.env.example.

API reference

EndpointReturns
GET /api/network Static route shapes (with shape_id + colour) and all stops. Fetched once by the frontend.
GET /api/vehicles The latest cached vehicle snapshot plus its age in seconds. Cheap — just memory, no upstream call.
GET /api/stop/{stop_id}/eta The next 3 predicted arrivals at a stop (soonest first), each joined to route / headsign / colour.
GET /api/trip/{trip_id}/next-stop The soonest upcoming stop for a trip — used when you click a vehicle to show its next stop + ETA.

Deployment

Single origin (default)

The app is single-origin: one FastAPI process serves both /api/* and the built React bundle, so it ships as one container. The multi-stage Dockerfile builds the frontend with Node and serves it with Python, binding 0.0.0.0:$PORT. A render.yaml Blueprint deploys it free on Render and auto-deploys on every push. 

docker build -t transit .
docker run --rm -p 8000:8000 -e PORT=8000 transit   # http://localhost:8000

Split: frontend on a CDN, backend as an API

Because the frontend is a static bundle and the backend is a plain JSON API, the two can be hosted separately. This is the recommended setup for a free tier, since a CDN-hosted frontend loads instantly while only the data waits for the backend to wake.

  • Frontend → a static host (Cloudflare Pages, Vercel, Netlify, GitHub Pages). Root frontend-react, build npm run build, output dist. Set VITE_API_BASE to the backend's origin (no trailing slash) at build time.
  • Backend → an API-only service (Render, Fly.io, Railway). Set ALLOWED_ORIGINS to the frontend's origin(s), comma-separated, to lock down CORS. Left unset it defaults to *, so single-origin keeps working unchanged.

Cold-start mitigations (free tier)

Free instances sleep when idle; the first request after a nap wakes the backend (re-downloading the static GTFS and restarting the poll), which takes ~30–60 s. Options, most effective first:

  1. Host the frontend on a CDN so the map UI loads instantly and only data waits — the in-app loading overlay covers that gap.
  2. Keep the backend warm with a free cron that pings /api/vehicles every ~10 min (cron-job.org, UptimeRobot, a scheduled GitHub Action).
  3. Cache the static GTFS to disk so wake-ups skip the re-download.
  4. Use an always-on tier (a paid plan, or a Fly.io machine that doesn't sleep).
