🚌 How the Live Transit Tracker Works

A student's walkthrough of the stack, the architecture, the data, and the GIS techniques that make buses glide smoothly along real roads in real time.

Python · FastAPI React · TypeScript MapLibre GL Turf.js GTFS / GTFS-Realtime
01 · The big picture

One backend, many browsers

The golden rule: browsers never talk to Calgary directly. One backend does the expensive work once, then hands cheap cached JSON to everyone.

Calgary → one backend → many browsers. The backend is the only thing that fetches.

Why? Decoding protobuf, joining the schedule, and de-duplicating can't happen in the browser. And if 100 people opened the map, you'd hit Calgary 100×. Do it once, cache it, serve JSON.
02 · The stack

What each piece is for

FastAPI — tiny Python web framework; serves the JSON API + the frontend.
requests — downloads the feeds (on a background thread).
gtfs-realtime-bindings — decodes Google's protobuf feed format.
React + TypeScript — the UI: reusable components, typed data contracts.
MapLibre GL — the map, drawn on the GPU from vector tiles.
react-map-gl — React wrapper around MapLibre (Map, Source, Layer, Popup).
Turf.js — the GIS math: project a point onto a line, walk along it.
zustand — a tiny store for the reactive UI state.
Two frontends, one backend. The current app is React + MapLibre (frontend-react/); the original Leaflet app (frontend/) still works and is kept as a fallback. The backend JSON contract never changed — the renderer was swappable without touching Python.

Two kinds of transit data

Static GTFS

A zip of CSVs: routes, trips, stops, and shapes (the exact path each route drives). Downloaded once at startup. Rarely changes.

GTFS-Realtime

Live protobuf feeds, refreshed ~every 30 s: vehicle positions (where each bus is) and trip updates (predicted arrival times per stop).

03 · The crucial join

A live bus knows almost nothing about itself

Calgary's live feed gives a position and a trip_id — but no route name, no color, no shape. We recover all of that from the static schedule using trip_id as the key.

Empirical finding: ~97.4% of live trip_ids resolve in the static schedule. The rest are added/unscheduled trips — handled gracefully as "unmatched", not treated as bugs.
04 · Smooth motion

The bus only "blinks" every 30 seconds

A new position arrives only ~every 30 s. If we teleported the marker it would jump. So we animate toward the latest known spot at 60 fps.

Interpolate, don't extrapolate

Interpolation ✓

Glide from where the marker is to the newest fix. A small, constant lag — but stable and artifact-free.

Extrapolation ✗

Guess ahead using velocity. With no speed/bearing in the feed and 30 s gaps, you get overshoot and correction "jitter."

Self-tuning glide: the animation duration is clamp(timeSinceLastMove, 12 s, 40 s), so the motion stretches to span the real gap instead of finishing early and freezing.
05 · The impressive GIS bit

Make buses follow the road, not cut across blocks

A straight line between two fixes cuts corners — buses look like they're flying. We snap each fix onto the route's shape and move along the line.

route shape (from GTFS) naive straight line snapped motion

How it works (linear referencing)

  1. Project the old and new positions onto the shape → turf.nearestPointOnLine gives "distance along the line."
  2. Interpolate that distance each frame and read back the point with turf.along. The marker rides the curve.
  3. Fallback: if a fix is > 50 m off its shape (detour, bad data, no shape), revert to the straight-line glide so nothing breaks.
Where do the road shapes come from? They're already in the static GTFS (shapes.txt) — one polyline per route, tracing the actual streets. No external map-matching or OpenStreetMap needed.
06 · Performance

~6000 stops without melting the browser

Putting 6000 image markers in the DOM at once is a known performance cliff — it's why the Leaflet app needed a clustering plugin. Clustering keeps what's drawn near what's on screen.

Same idea, two costs avoided: fewer things drawn (speed) and less visual clutter (clarity). Below zoom 16 stops cluster; at/above 16 they split apart.
MapLibre makes this almost free. The React app draws all 6000 stops as one GPU layer with built-in clustering (cluster:true on the GeoJSON source) and automatic label declutter — no plugin, and the old "perf cliff" constraint simply goes away.
07 · The signature feature

Tracking a bus to your stop

Click a stop (or a bus) → pick an arrival → Track. The camera follows the bus, it flashes blue, a blue line shows its path to your stop, and a bubble counts down.

The ETA → due → Late → departed lifecycle

  • ETA / Late — measured against the predicted time captured when you started tracking (anchored — it won't silently re-base). Past it → red Late: counting up.
  • due — based on real distance along the route to the stop (not the drifty clock), so it triggers when the bus is genuinely close.
  • departed — once the bus is measurably past the stop → tracking ends and the camera flies back.
Why distance, not just the clock? Predictions drift and the bus snaps to the road centre-line (offset from the curb). Measuring distance along the shape reaches ~0 exactly at the stop, so "due" is honest.
08 · How the code is organised

Two worlds: a map engine and React chrome

The React app's most important idea is a split: the 60 fps map work is imperative and lives outside React; everything React renders is reactive and lives in a tiny store.

The engine (imperative)

lib/engine.ts owns the per-vehicle animation + tracking and, every frame, writes a GeoJSON blob straight into the MapLibre map (source.setData()). It never touches React.

The store (reactive)

store.ts (zustand) holds just the chrome state — caption, zoom, what's tracked, the ETA text, the open popup — updated 1–5×/s. Components re-render from it.

Why the split? Driving a 60 fps loop through React state would re-render the UI hundreds of times a second. Keeping the hot path in the engine and the cool path in React is what makes it both smooth and tidy.
