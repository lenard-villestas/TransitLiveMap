Project layout

A FastAPI backend (the "kitchen") decodes Calgary's GTFS-realtime feeds, joins them to the static schedule, caches the result, and serves clean JSON + the static frontend. The frontend is vanilla ES modules over Leaflet.

backend/
  server.py        FastAPI app, 15s poll loop, /api/* endpoints, serves ../frontend
  build_map.py     static-GTFS loaders + build_vehicles / build_stops / build_shapes
  explore_feed.py  Phase-0 feed explorer; fetch_feed(url) is shared
  verify_join.py   trip_id → route join coverage diagnostic
frontend/
  index.html       markup only; loads /styles/app.css + <script type="module">
  styles/app.css   all styling
  scripts/*.js     ES modules (config, state, format, geometry, icons, map,
                   network, vehicles, tracking, geolocation, main)
  static/          bus.png, train.png, bus-stop.png
docs/              this reference + presentation.html

End-to-end data flow

  1. Startup: load_network() downloads the static GTFS zip once, builds in-memory lookups (routes, trips, shapes, stops).
  2. Background thread: poll_loop() fetches the vehicle positions and trip updates feeds every 15 s, dedupes on the feed's header timestamp, resolves trip_id → route/shape, and atomically replaces the cached SNAPSHOT + TRIP_UPDATES indexes.
  3. Frontend: fetches /api/network once (shapes + stops), then polls /api/vehicles every 15 s. A 60 fps requestAnimationFrame loop interpolates each vehicle along its route shape between fixes.
  4. Interaction: clicking a stop or vehicle calls /api/stop/{id}/eta or /api/trip/{id}/next-stop; "Track" starts the follow-cam + ETA bubble.

Backend — server.py

Why a backend at all

Clients never hit Calgary's feed directly. The backend decodes protobuf (gtfs-realtime-bindings), does the static join, dedupes, caches, and serves clean JSON. Without it every client would hammer Calgary and you couldn't do the join or spatial work.

Why a thread, not async

requests.get() blocks. Running it on the FastAPI event loop would freeze every HTTP response during a poll, so the poller runs on a daemon thread.

Key globals: NETWORK (shapes+stops), SNAPSHOT (latest vehicles), TRIP_UPDATES ({index, by_trip, ts}), LOOKUPS (routes+trips). A @app.middleware("http") sets Cache-Control: no-store so dev edits always reload. The frontend is served by one catch-all StaticFiles mount at / (after the /api/* routes, which keep priority).

build_trip_index(feed) turns the trip-updates feed into two indexes: index = {stop_id: [(arrival, trip_id, vehicle_id)]} (stop ETA) and by_trip = {trip_id: [(arrival, stop_id)]} (a trip's upcoming stops). Every optional protobuf field is guarded with HasField().

HTTP endpoints

GET /api/stop/{stop_id}/eta {stop_id, arrivals:[{route,headsign,color,type,trip_id,vehicle_id,arrival,eta_seconds}], ts} — soonest 3, past filtered.

GET / · /styles/* · /scripts/* · /static/* The frontend/ folder (static mount, html=True).

explore_feed.py / verify_join.py

fetch_feed(url) (in explore_feed.py) GETs protobuf bytes and parses them into a FeedMessage — shared by the server for both feeds. The rest of explore_feed is a CLI inspector (--watch, --vehicle, schema dump). verify_join.py measures what fraction of live trip_ids resolve in the static schedule (~97.4%).

Data contracts (keep backend + frontend in sync)

Vehicle array (build_vehicles ↔ vehicles.js destructure):

[lat, lon, route_short, color, headsign, vehicle_id, route_type, trip_id, shape_id]

Stop array: [lat, lon, name, stop_id]  ·  Shape: {shape_id, coords, color}

trip_id links a vehicle to a trip-updates arrival; shape_id links it to its road polyline (for snapping + the blue tracked route).

Calgary GTFS-RT quirks (discovered empirically)

FieldPopulated?Consequence
trip.trip_id✅ 100%The only reliable vehicle→route link.
trip.route_id (positions)❌ 0%Join via trip_id instead.
position.bearing / speed❌ 0%Compute bearing from positions; no dead-reckoning.
stop_time_update.stop_id✅ 100%Matches static stops.txt — clean ETA join.
trip_update.vehicle.id❌ emptyLink arrivals to live buses by trip_id, not vehicle id.

Route types in Calgary: only 0 (CTrain/LRT) and 3 (bus, incl. MAX BRT). Publish cadence ≈ 30 s; we poll at 15 s and dedupe on the header timestamp so faster polling is free.

Frontend — module graph

CDN libraries (L Leaflet, markercluster, turf) load as classic scripts and are used as globals. App code is ES modules:

main ─┬─ map ──────────── (creates the Leaflet map, layers, cluster)
      ├─ network ──────── map, state, icons, format
      ├─ vehicles ⇄ tracking   (intentional cycle; function-level only)
      │     └─ config, state, geometry, icons, format
      ├─ tracking ─────── config, map, state, geometry, icons, format, vehicles
      └─ geolocation ──── map, config, state
state.js  →  shared singletons (veh, vehByTrip, stopMarkers, shapesById, app{…})

config.js / state.js / format.js

  • config — constants: API, REFRESH_MS, DUE_M=50, DEPART_M=20, OFFROAD_M=50, DISABLE_CLUSTER_ZOOM=16, RETURN_ZOOM=16 + ICONS.
  • state — the encapsulated stand-in for globals: collections veh, vehByTrip, stopMarkers, shapesById and the app object holding reassignable fields (tracked, etaTimer, lastPan, routeLine, preview*, …). Other modules mutate app.x.
  • format — esc (HTML-escape), etaPhrase (ETA:/Late:), etaParts (adds a "due" window for stop-popup rows).

geometry.js / icons.js

  • geometry — bearingDeg, plus Turf wrappers projectOnLine (nearest point on a shape → distance-along + offset), pointAt (point at a distance along), shapeBearing, lerp. Turf uses [lng,lat]; the app uses [lat,lon] — converted at the boundary.
  • icons — kindFor(type), makeIcon(kind, short) (vehicle divIcon + route label), stopDiv(selected) (stop pin).

map.js / network.js

  • map — builds the Leaflet map, CARTO basemap, shapeLayer, the stopCluster (markercluster with themed badges, disableClusteringAtZoom), the layer control, and updateZoomCap() (zoom readout + reveals route labels at zoom ≥ 16).
  • network — loadNetwork() draws the polylines, caches a Turf line per shape_id, and adds each stop to the cluster with a bind-once popup that fetches ETA on popupopen (binding inside a click handler double-wires Leaflet's toggle and breaks reopening). renderEtaPopup() builds the rows; its Track button calls window.trackIdx(i).

vehicles.js — the animation engine

  • refresh() — fetch /api/vehicles; create/update a marker per vehicle; rebuild vehByTrip; remove vehicles that left the feed.
  • setTarget() — on a new fix, project both the current and new positions onto the vehicle's shape. If within OFFROAD_M → mode:'shape' (store along-line distances); else mode:'line' (straight lerp).
  • animate() — 60 fps loop: in shape mode, lerp the along-line distance and place the marker with pointAt; runs the follow-cam and trims the blue route (throttled).
  • openVehicleNext() — click a bus → fetch its next stop, preview-highlight the bus + stop, open a popup with a Track button.

tracking.js

  • track / untrack — start/stop tracking: declutter stops, glow the bus + its stop, bind the ETA tooltip, follow-cam, draw the blue route; untrack restores everything and (optionally) flies back to the stop.
  • trackedBubble() — computes the status: due when within the along-route window, departed once past it, else ETA: / Late: against the anchored arrival epoch (captured at track start, never re-based by later predictions).
  • drawTrackedRoute() — turf.lineSliceAlong from the bus's current along-distance to the stop, updated in place each frame.
  • updateBubble / updateTrackBar — the floating bubble + bottom bar (stop name on top, labeled timer below, red when late).

geolocation.js / main.js

  • geolocation — a "📍 locate me" Leaflet control + a "you are here" dot; startLocate() centres the map on the user at zoom 16 on load.
  • main — the entry point: exposes the four popup-button handlers on window, wires map events, starts the rAF loop, loads the network, and begins the 15 s poll.
